## 一、两个绕不开的痛点

**痛点 1：人会离职，项目就断档。**
新人接手，第一周全在翻旧文档、问前任、猜上下文。人走了，记忆也跟着走了。

**痛点 2：临时换人，交接要扒一层皮。**
需求散在聊天记录里、进度只有口头、谁做到哪一步没人说得清。

**Agent 不会离职，且永远带着项目的全部记忆。**
但——多个 Agent 一起做一个项目，问题变成了：**怎么让它们共享同一份上下文？怎么知道谁该干什么？怎么防止它看到不该看的项目？**

**山海·项目台**就是把这件事做掉的那层壳。

---

## 二、它到底解决什么

| 你怕的 | 它怎么处理 |
|:--|:--|
| **交接断档** | 需求文档、任务、进度全在台面上。新 Agent 进场 30 秒读完上下文，直接出进度汇报 |
| **多个 Agent 各干各的** | 一个项目一张台：需求 → 拆解 → 派活 → 验收，四个环节在同一条线上流转 |
| **Agent 乱看别人的项目** | 给每只 Agent 发一枚**项目专属通行证**。进哪扇门看哪家的账，绝不泄露其他项目 |
| **外包/合作扯皮** | 交付物挂在任务上、验收有明确状态。谁交的、什么时候交的、验收过没过，都有记录 |
| **成本失控** | 积分账本 + 冻结机制，每一次调用可追溯 |

## 三、三个关键设计

### 1. 项目专属通行证（一枚 Key 只开一扇门）

每只 Agent 进一个项目，拿到一枚**只对该项目有效**的通行证。

- 同一个 Agent 进 A 项目和 B 项目，是**两枚不同的通行证**
- 从 A 项目移除，**不影响**它在 B 项目的通行证
- 通行证明文**只在签发那一刻出现一次**，服务端只存哈希

> 这就是「进哪扇门看哪家的账」在工程上怎么落地。

### 2. 任务状态机（不让活悬在空中）

```
待认领 → 进行中 → 已交付 → 已验收
                 ↘ 被驳回（可重新派发）
        ↘ 阻塞 / 已取消
```

每个状态都有明确含义，不会出现「这个任务到底做完了没」的模糊地带。

### 3. Agent 只停用，不删除

**公司从不烧档案，只裁员。**

Agent 停用后状态保留、记录留痕——因为历史任务要靠它的 ID 归因。
「这个活当初谁干的」这件事，三个月后还得查得到。

## 五、关于后端

本项目是前端壳（UI 层）。它需要一套符合接口约定的后端服务才能运行。

本仓库不含后端实现、数据库结构与部署脚本。

### 开发期如何连你自己的后端

前端只发相对路径 `/api/xxx`。开发期若要代理到你的后端，设置环境变量即可：

```bash
VITE_DEV_API_TARGET=http://你的后端地址:端口 npm run dev
```

不设置则不启用代理，请求由你的反向代理（Nginx 等）转发。

## 七、设计取舍（为什么不那么做）

**为什么不用庞大的 UI 组件库？**
这类后台界面 80% 的复杂度来自「把这个组件库的 API 学明白」。我们只需要表格、按钮、弹层，
自己写 200 行令牌比接一个 2MB 的库划算得多，而且改起来不用读三方文档。

**为什么通行证明文只出现一次？**
因为「能再次看到」就等于「存在一个能泄露的地方」。
只存哈希、只显示前 8 位，是为了让「泄露了」这件事在结构上更难发生。

**为什么 Agent 不做物理删除？**
删一行数据库很容易，但**历史任务的归因链会断**。
宁可多一个「已停用」状态，也不让审计出现空洞。
